The ipn.arpa Zone and IPN DNS Operations

Abstract

This document requests a DNS parent for IPN addresses, discusses the registration procedures and management of the DNS zone, as well as some operational recommendations. This document specifies that IPN addresses may have a DNS representation of the form 1.978879.ipn.arpa, for IPN node 1 under IPN Allocator 978879.¶

This document also describes how this DNS structure can be useful in locating the Bundle Protocol (BP) Convergence Layer (CL) endpoint(s) of the BP Agent responsible for a given IPN address.¶

2. Conventions and Definitions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.¶

This document uses the following terms as defined in [RFC9758]:¶

Allocator Identifier:

A 32-bit unsigned integer identifying the Allocator that assigned a Node Number (Section 3.2 of [RFC9758]).¶

Node Number:

A 32-bit unsigned integer identifying a node in the context of an Allocator (Section 3.3 of [RFC9758]).¶

Fully Qualified Node Number (FQNN):

The combination of an Allocator Identifier and a Node Number, which uniquely identifies a node (Section 3.3.1 of [RFC9758]). As in [RFC9758], an FQNN is written as (Allocator Identifier, Node Number); for example, (978879,2).¶

Service Number:

An unsigned integer identifying a service on a node (Section 3.5 of [RFC9758]).¶

ipn URI:

A URI using the 'ipn' URI scheme. An ipn URI comprises an Allocator Identifier, a Node Number, and a Service Number; that is, an FQNN plus a Service Number (Section 3 of [RFC9758]). An ipn URI used as a Bundle Protocol Endpoint Identifier (EID) is termed an "ipn EID" (Section 5 of [RFC9758]).¶

This document defines the following terms:¶

DNS base name:

The DNS name beneath ipn.arpa that represents an FQNN, constructed as specified in Section 3.1.¶

CL-specific query name:

A DNS name, defined by a CL specification relative to a DNS base name, at which a BP Agent queries for the records needed to reach the node using that CL. For example, the TCPCLv4 query name is formed by prepending _dtn-bundle._tcp to the DNS base name.¶

3. Concept of Operations

The Forwarding Information Base (FIB) of a BP Agent may be populated from a variety of sources. Typically, explicit (manual) configuration is given to associate BP destination endpoints with the Convergence Layer parameters required to establish communication with a responsible receiving BP Agent.¶

A BP Agent may also dynamically create a FIB entry by querying for DNS Resource Records as described in this section.¶

3.1. Discovery Model

The ipn.arpa zone is an infrastructure namespace derived from IPN identifiers. Discovery is keyed on the FQNN of the destination node.¶

Before constructing a DNS name, a BP Agent MUST parse and interpret the destination ipn URI or ipn EID according to [RFC9758], yielding numeric values for its Allocator Identifier, Node Number, and Service Number. This includes the text syntax rules of Section 4 of [RFC9758] and the CBOR decoding rules of Section 6.2 of [RFC9758]. In particular, an Allocator Identifier omitted from the text representation means zero, the Default Allocator (Section 3.2.2 of [RFC9758]). An omitted Allocator Identifier does not cause the allocator label to be omitted from the DNS name.¶

For Allocator Identifier A and Node Number N, the DNS base name MUST be:¶

N.A.ipn.arpa.
¶

Each of N and A MUST be represented as a single label containing its unsigned decimal value, using ASCII digits without leading zeroes. The value zero is represented by the single digit "0". The labels are not padded to a fixed width and are not split into individual digits.¶

The Service Number does not participate in construction. All ipn URIs that share an FQNN map to the same DNS base name.¶

Table 1: Example DNS Base Names
ipn URI DNS base name
ipn:978879.2.345 2.978879.ipn.arpa.
ipn:978879.2.0 2.978879.ipn.arpa.
ipn:16384.345 16384.0.ipn.arpa.
ipn:0.16384.345 16384.0.ipn.arpa.

Because the DNS base name is constructed from the parsed numeric components rather than from the text of the URI, equivalent representations of the same FQNN produce the same DNS base name. For example, ipn:16384.345 and ipn:0.16384.345 both identify the FQNN (0,16384). Likewise, the two-element and three-element CBOR encodings of an ipn EID (Section 6.4 of [RFC9758]) produce the same DNS base name.¶

The DNS base name is distinct from the CL-specific query name at which a BP Agent queries for records. For example, a BP Agent discovering TCPCLv4 [TCPCL] service for the FQNN (978879,2) prepends _dtn-bundle._tcp to the DNS base name and queries for SRV records [RFC2782] at:¶

_dtn-bundle._tcp.2.978879.ipn.arpa.
¶

No preliminary PTR query is required, and this discovery procedure requires no PTR records.¶

This differs from the conventional use of in-addr.arpa and ip6.arpa, in which a PTR record maps an address to a hostname that is then used for further lookups. The discovery procedure in this document publishes service records directly beneath the DNS base name; no IPN-to-hostname mapping step is involved.¶

The Null ipn URI (Section 3.1 of [RFC9758]) and LocalNode ipn URIs (Section 3.4.2 of [RFC9758]) are recognized after the interpretation described above. For example, an ipn URI with a zero Allocator Identifier, a zero Node Number, and a non-zero Service Number is treated as the Null ipn URI (Section 3.4.1 of [RFC9758]), and ipn:!.7 is a LocalNode ipn URI. Neither identifies a remote destination for this procedure: the Null endpoint has no members, and a bundle destined for a LocalNode ipn EID is not allowed to leave the local node (Section 5.4 of [RFC9758]). A BP Agent MUST NOT perform DNS discovery for the Null ipn URI or for a LocalNode ipn URI. In addition, Section 5.4 of [RFC9758] prohibits publishing LocalNode ipn EIDs in any node identification directory, such as a DNS registration.¶

These cases are identified by the complete FQNN: (0,0) for the Null ipn URI and (0,4294967295) for LocalNode ipn URIs. This document does not reserve Node Number 0 or Node Number 4294967295 under any other Allocator Identifier. For example, the FQNNs (978879,0) and (978879,4294967295) are processed like any other FQNN.¶

3.2. Examples

The two examples in this section show alternative DNS configurations for the same node. In both, a BP Agent (perhaps collocated at a ground station) has received a Bundle destined for ipn:978879.2.345 and uses TCPCLv4 [TCPCL]. An operator publishes either the configuration of Example A or the configuration of Example B, not both: the SRV RRset of Example A and the CNAME of Example B must not be published together at the same owner name (see Section 3.3).¶

The records shown are zone excerpts; routine SOA and NS records are omitted.¶

3.2.1. Example A: Service Records in the Allocator's Zone

In this configuration, the SRV records are published directly in the allocator's zone.¶

; Relevant records in 978879.ipn.arpa.
$ORIGIN 978879.ipn.arpa.
_dtn-bundle._tcp.2  3600 IN SRV 0 0 4556 antenna-relay.space-agency.example.

; Relevant records in space-agency.example.
$ORIGIN space-agency.example.
antenna-relay  3600 IN A    192.0.2.1
antenna-relay  3600 IN AAAA 2001:db8::1
¶

The BP Agent:¶

  1. constructs the query name _dtn-bundle._tcp.2.978879.ipn.arpa. from Allocator Identifier 978879 and Node Number 2 of the destination ipn:978879.2.345;¶

  2. queries for SRV records at _dtn-bundle._tcp.2.978879.ipn.arpa., receiving an SRV record with port 4556 and target antenna-relay.space-agency.example.;¶

  3. queries for A and AAAA records at antenna-relay.space-agency.example., receiving 192.0.2.1 and 2001:db8::1; and¶

  4. attempts a TCPCLv4 connection to [2001:db8::1]:4556 or 192.0.2.1:4556 and, once a session is established, transfers the Bundle.¶

3.2.2. Example B: Service Lookup Redirected through a CNAME

In this configuration, the allocator's zone contains a CNAME that redirects the service lookup to a name in the service operator's zone, where the SRV records are published.¶

; Relevant records in 978879.ipn.arpa.
$ORIGIN 978879.ipn.arpa.
_dtn-bundle._tcp.2  3600 IN CNAME _dtn-bundle._tcp.mars-orbiter2.space-agency.example.

; Relevant records in space-agency.example.
$ORIGIN space-agency.example.
_dtn-bundle._tcp.mars-orbiter2  3600 IN SRV 0 0 4556 antenna-relay.space-agency.example.
antenna-relay  3600 IN A    192.0.2.1
antenna-relay  3600 IN AAAA 2001:db8::1
¶

The BP Agent starts with the same query as in Example A: it queries for SRV records at _dtn-bundle._tcp.2.978879.ipn.arpa.. Ordinary DNS resolution follows the CNAME at that name to _dtn-bundle._tcp.mars-orbiter2.space-agency.example. and returns the SRV RRset found there, with port 4556 and target antenna-relay.space-agency.example.. There is no separate preliminary CNAME query. Resolution of the A and AAAA records at antenna-relay.space-agency.example. and establishment of the TCPCLv4 connection then proceed as in Example A.¶

This configuration divides administrative responsibility: the allocator's zone maintains only the alias, while the service operator maintains the SRV records in its own zone and can change them without further changes to the allocator's zone.¶

3.2.3. Onward Forwarding

In these examples, antenna-relay.space-agency.example. is configured to accept Bundles for onward forwarding to node 2. Establishing a TCPCLv4 connection to that relay does not change the Bundle's destination EID, which remains ipn:978879.2.345, and does not imply that the spacecraft is currently reachable. Forwarding the Bundle toward node 2 is the relay's responsibility.¶

3.3. DNS Constraints

The following DNS behaviors apply to the configurations above:¶

  • A CNAME aliases only its own owner name Section 3.6.2 of [RFC1034]. To redirect the service lookup, the CNAME is placed at the complete service owner name (e.g., _dtn-bundle._tcp.2.978879.ipn.arpa.). A CNAME at the bare node name (e.g., 2.978879.ipn.arpa.) does not alias its descendants and so does not redirect the service lookup.¶

  • A CNAME record and an SRV RRset cannot coexist at the same owner name Section 3.6.2 of [RFC1034].¶

  • The Target of the SRV record eventually obtained must have one or more address records and must not be an alias [RFC2782].¶

3.4. Other Convergence Layers

Each CL specification that uses DNS for discovery defines its own service query names and record types (e.g., SRV or SVCB records) relative to the DNS base name. Appropriately capable BP Agents query for those records using the same DNS base name.¶

6. IAB Considerations

In accordance with the procedure in Section 3 of [RFC3172], the IAB is requested to approve the zone "ipn.arpa" as an infrastructure namespace derived from IPN identifiers. Names in this zone are constructed from IPN Allocator Identifiers and Node Numbers and are usable for service discovery, such as locating the CL endpoint(s) of the BP Agent responsible for a given IPN node (see Section 3).¶

This follows the precedent of e164.arpa [RFC6116], in which names are derived from E.164 telephone numbers and queried directly for service records (NAPTR).¶

Per Section 3.3.1 of [RFC9758], the FQNN of a node comprises a 32-bit Allocator Identifier and a 32-bit Node Number. Those two components determine the DNS base name (see Section 3.1).¶

7. IANA Considerations

7.1. Creation of ipn.arpa

Following approval by the IAB in accordance with Section 3 of [RFC3172], IANA is requested to add "ipn.arpa" to the ".arpa" domain. This namespace supports DNS names derived from IPN Allocator Identifiers and Node Numbers, as specified in this document (see Section 3).¶

"0.ipn.arpa" corresponds to Allocator Identifier zero, the Default Allocator (Section 3.2.2 of [RFC9758]). It is treated like the IN-ADDR.ARPA zones for the private address space of [RFC1918] (Section 4.1 of [RFC6303]): it has only local significance. A "0.ipn.arpa" zone MAY exist in local DNS resolvers or servers that serve it authoritatively as a locally served zone [RFC6303], but a populated "0.ipn.arpa" zone MUST NOT ever be published in the global DNS.¶

7.2. 'ipn' Allocator Registry List of Nameservers

IANA is requested to augment its registration procedures for entries in the 'ipn' Scheme URI Allocator Identifiers Registry with a column for "Authoritative Nameservers". Requesters of an Allocator or Allocator range MAY provide the IP addresses of DNS nameservers that will be considered authoritative for the .ipn.arpa zone for each requested Allocator.¶
